# 产品策略：DSH × VS Code —— 桥，不是 Agent（product-strategy）

**日期**: 2026-08-18 ｜ **状态**: 待评审
**来源**: [market-analysis.md](market-analysis.md)、[advise-by-gemini.md](advise-by-gemini.md)（Gemini 提案评估）、[architecture/proposal-by-deepseek.md](../architecture/proposal-by-deepseek.md)
**现状与差距依据**: 见 [product-gap.md](product-gap.md)（基于 v0.0.10 代码与 DSH 协议的事实 + 逐项差距）

## 1. 定位（一句话）

**我们是 DeepSeek Harness（DSH）与 IDE 之间的桥**：把 DSH 的完整能力（Everything is a Plugin / Workflow / Goal / 多模型）带进 VS Code 的编辑器体验，同时把 IDE 的上下文（选区、文件、诊断、Git）喂给 DSH。**我们不写 coding agent，我们让 DSH 成为更好的 coding agent。**

**价值标尺：用户便捷性 > 界面一致性。** 桥的价值在于减少用户操作（少复制粘贴、少切换窗口、少起进程、少手动同步），而不是把 DSH 的网页 UI 换成 VS Code 原生控件——DSH 的 UI 是官方产品，能用就好用，不为了"原生感"而重做。

## 2. 价值（VALUE）—— 我们交付什么

> **一句话**：*在你不离开代码的地方，用上 DSH 的全部能力——省的是切换，留的是思路。*

| 价值层 | 用户感知 | 举例 |
|---|---|---|
| **高效便捷**（直接价值） | 省时省力 | 少切换窗口、少复制粘贴、少起进程、少手动同步 |
| **心智连续**（隐性价值） | 不打断思路 | 写代码→问 DSH→看结果→跳文件，全程一个上下文；保住工作记忆，不重建语境 |
| **零成本接入**（获客价值） | 不迁移就升级 | 同一个 `~/.dsh`、同一份会话/设置；终端/浏览器用户换到 IDE 零学习成本；新用户一条命令跑起来 |
| **生态放大**（能力价值） | 更强的 DSH | DSH 的 Workflow/Goal/多模型能力 × IDE 的选区/文件/诊断上下文；能力不变，更好够到 |

**价值判据**：每项功能上线前先问——"它让用户少做了什么？" 答不上来的，不做（见 §8 反模式）。

## 3. 现状与差距（结论摘要）

> 事实清单与逐项差距分析见 [product-gap.md](product-gap.md)，本节只留结论。

- **差距的本质**：当前是"网页进 IDE"，尚未是"IDE 上下文进 DSH"——桥是通的（DSH 全部 API 可达），缺的是**把编辑器侧的能力接上桥**（注入/跳转/编排）；
- **生命周期缺口**：切工作区 = dsh 被杀 + 面板关 + 重开 + 手动切 DSH 工作区——**这是"心智连续"价值的最大破坏点**，优先级应高于纯体验优化；
- **架构定盘（协议事实）**：DSH **单实例即可多会话并行、各绑 cwd**（workspace/模型是会话级属性）——"多实例管理"不是必需，重点转为 **G-02 工作区联动（会话级切换）+ 多会话面板编排**；
- 因此 v0.1.x 的 P0 全部是"桥侧接线"工作，不碰 DSH。

## 4. 边界（做什么 / 不做什么）

```
做（壳层 + 桥）                      不做（DSH 的事）
─────────────────────────────       ─────────────────────────────
· 启动/托管 dsh 进程                 · 对话/工具/编排引擎
· 内嵌 Web UI（编辑器标签页）         · 权限系统（DSH 已有 presets）
· 传输桥（fetch/WS/剪贴板）           · 工具执行后端（bash/pwsh）
· IDE 上下文注入（选区/文件/诊断）     · Diff 写前审查（需上游）
· 多面板/多会话编排                   · @ 引用补全（需上游）
· attach / 工作区联动（T13/G-02）     · 终端委派（需上游）
```

**判定原则**：一件事若 DSH 前端/后端已能做 → 壳层只"暴露/编排"，不重造；若需要改 DSH 前端行为或工具后端 → 提上游，不本地 hack（零 fork）。

| 双会话并排编排（多面板实例） | 高效便捷 | v0.3.x P2 |

## 6. 与上游的分工（长期竞争力）

| 能力 | 归属 | 动作 |
|---|---|---|
| Diff 写前审查 / 写盘钩子 | DSH 工具层 | 上游 issue/PR（"write review 模式"） |
| 工具执行委派到 IDE 终端 | DSH 工具后端 | 上游 issue/PR（执行后端抽象） |
| `@` 富上下文补全 | DSH 前端 `ui-input-trigger` | 上游 issue/PR（开放引用源插件） |
| `isLoopback` 声明（webview 嵌入） | DSH `client-connection` | 上游 issue/PR（小，G-05） |
| 桥协议沉淀为 DSH 插件协议 | 双方 | 上游共建（Gemini §6 生态价值，认可） |

**策略**：我们是 DSH 官方生态的"IDE 合作层"。上游合入 = 能力落地；未合入前，壳层只做桥内能做到的（不 hack 前端）。

## 8. 反模式（明确不做）

- ❌ 把 DSH 前端拆开注入 IDE 原生控件（破坏零 fork、失去官方更新）
- ❌ 壳层重造权限/终端/Diff 引擎（与 DSH 抢活，且质量必然落后）
- ❌ 静默自动切换工作区（破坏 DSH 会话与 cwd 的绑定，需用户确认）
- ❌ 把 DSH 网页 UI 重做成 VS Code 原生控件（DSH 的 UI 是官方产品；只做桥的体验增强，不做 UI 迁移）
- ❌ 为"原生感"而做的 UI 迁移（不通过 §2 价值判据的功能）

## 9. 成功标准（桥视角）

- 用户能**不离开 VS Code** 完成"选代码 → 问 DSH → 看答案 → 跳转文件 → 确认改动"闭环；
- DSH 生态侧：上游合入 ≥2 项我们的提案（证明"IDE 合作层"价值）；
- 双 IDE（VS Code + Antigravity）体验一致。
